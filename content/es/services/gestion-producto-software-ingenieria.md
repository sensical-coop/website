El software de ingeniería tiene una vida larga, y sus usuarios dependen de él cada día para obtener sus resultados. Gestionamos productos como estos: {{< accent >}}convertimos lo que piden los ingenieros en una hoja de ruta, especificaciones y versiones{{< /accent >}} que un equipo de desarrollo pequeño pueda entregar, sin romper aquello de lo que dependen los usuarios actuales.

{{< alert type="bg-sensical" >}}

### El problema

Una aplicación de ingeniería madura acumula peticiones más deprisa de lo que cualquier equipo puede desarrollarlas: un nuevo formato de datos, un cálculo exigido por una nueva normativa, una integración con un banco de ensayo, un informe específico para un cliente. Cada una tiene sentido por sí sola. Sin una forma clara de elegirlas, especificarlas y entregarlas, el producto pierde el rumbo, las versiones se retrasan y el soporte acaba absorbiendo al equipo. La gestión de producto consiste en hacer explícitas esas decisiones y convertirlas en software.

{{</alert>}}

## Nuestra experiencia

Desde hace varios años gestionamos la evolución de [UniPlot](/es/proyectos/uniplot/), una aplicación de análisis, visualización e informes de datos que utilizan ingenieros de ensayo y de simulación. El trabajo abarca todo el producto: hoja de ruta y requisitos, coordinación con los desarrolladores, versiones, add-ins para ámbitos específicos como el [cálculo de emisiones](/es/proyectos/calculo-emisiones/), licencias, documentación, formación y el material público del producto.

## Para quién

+ **Editores de software de ingeniería** con un producto maduro, una larga lista de peticiones de clientes y un equipo pequeño.
+ **Departamentos de ingeniería** que tienen herramientas propias y necesitan que evolucionen como un producto, no como una colección de scripts.
+ **Socios tecnológicos** que quieren conectar su software con otro producto y necesitan a alguien que se haga cargo del alcance conjunto.

## Qué ofrecemos

+ **Hoja de ruta y priorización**: recoger las peticiones de usuarios, soporte y ventas, y decidir qué entra en cada versión y por qué
+ **Requisitos y especificaciones**: funcionalidades descritas con casos de uso, criterios de aceptación y datos de prueba, redactadas para que los desarrolladores puedan estimarlas y desarrollarlas
+ **De peticiones puntuales a funcionalidades reutilizables**: decidir si la petición de un cliente corresponde al producto base, a un add-in, a un script o a un servicio, y convertir los desarrollos pagados por un cliente en algo que también aproveche al resto de usuarios
+ **Estimaciones de esfuerzo y casos de negocio**: paquetes de trabajo, decisiones entre desarrollar o integrar, y los argumentos técnicos que respaldan una nueva capacidad
+ **Coordinación del desarrollo**: backlog, análisis de incidencias, prototipos, validación técnica y preparación de versiones, con desarrolladores internos o externos
+ **Modelos de licencia en el producto**: trasladar la forma en que se vende un producto (licencia perpetua, alquiler, licencias flotantes, add-ins) a un comportamiento del software y un despliegue que funcionen para usuarios y administradores
+ **Coherencia del producto**: asegurarnos de que las condiciones de licencia, la documentación, las implicaciones de privacidad de funciones como las estadísticas de uso y el propio software dicen lo mismo
+ **Material de lanzamiento**: notas de versión, documentación, formación, webinars, folletos y webs que explican el producto a los ingenieros

{{< alert type="border-sensical" >}}

### Lo que no somos

Coordinamos las restricciones técnicas, comerciales y legales para que el producto sea coherente, pero no somos abogados ni damos asesoramiento jurídico. Cuando una cuestión lo requiere, la preparamos para tu asesoría jurídica.

{{< /alert >}}
